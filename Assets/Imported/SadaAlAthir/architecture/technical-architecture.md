# صدى الأثير — المعمارية التقنية المقترحة

## 1. المبدأ المعماري

تُبنى اللعبة على فصل واضح بين **البيانات** و**الأنظمة** و**المحتوى**. تكون حالات الأثير، العقد السردية، تعريفات التفاعل، وإعدادات الصوت بيانات قابلة للضبط، بينما تبقى الأنظمة مسؤولة عن تنفيذ القواعد العامة. يمنع هذا الفصل تكرار المنطق داخل العناصر الفردية ويجعل التوطين والاختبار والتوسعة أقل كلفة.

## 2. طبقات النظام

| الطبقة | المسؤولية | أمثلة |
|---|---|---|
| Core | دورة الحياة، التسجيل، الرسائل العامة، إعدادات المشروع | GameInstance، Subsystems، Message Bus |
| Gameplay | الحركة، التفاعل، الأثير، الحالة السردية | Player، Interaction، Ether |
| Presentation | الكاميرا، الواجهة، الصوت، المؤثرات | HUD، Audio، VFX |
| Data | تعريفات ثابتة وقابلة للضبط | Data Assets، Data Tables، Curves |
| Save | التقدم، الحالة، الإصدار والترحيل | SaveGame، Save Schema |
| Tools | التحقق من الأسماء، تقارير الأصول، فحوص الجاهزية | خارج المحرك مبدئياً |

## 3. الأنظمة المقترحة

### 3.1 Ether Perception System

يستقبل موقع اللاعب، اتجاه النظر، حالة الإدراك، ومصادر الإشارة. يعيد قائمة إشارات مرشحة مرتبة بحسب القرب، الوضوح، الأهمية السردية، وحالة التقدم. لا يقرر النظام معنى الإشارة؛ بل يرسل معرفاً إلى طبقة السرد.

### 3.2 Interaction System

يوحد التفاعل مع العناصر من خلال تعريف موحد: معرف التفاعل، شروط الإتاحة، النص المحلي، مدة التنفيذ، النتيجة، وربط الإشارة أو العقدة السردية. يجب أن يكون التفاعل قابلاً للإلغاء وآمناً عند إعادة التنفيذ.

### 3.3 Narrative State System

يدير متغيرات السرد والعقد المكتشفة والحالات المتفرعة. ينبغي أن تكون التغييرات على شكل أحداث مسماة، لا تعديلات متناثرة على متغيرات مجهولة. كل حدث يسجل مصدره ونسخته وقابلية تكراره.

### 3.4 Audio Intent Layer

يفصل نية الصوت عن ملف الصوت نفسه. تعريف الإشارة يحتوي على المعنى، الأولوية، النطاق، شروط التشغيل، ومفتاح التوطين؛ أما اختيار المقطع الصوتي النهائي فيتم عبر طبقة الربط الصوتي.

### 3.5 Save/Load Layer

يعتمد مخطط حفظ إصدارياً. يتضمن الحد الأدنى: نسخة المخطط، المنطقة الحالية، العقد المكتشفة، حالات الألغاز، خيارات المستخدم، ومؤشر آخر نقطة حفظ. أي تغيير غير متوافق يحتاج إلى خطة ترحيل موثقة.

## 4. واجهات البيانات المقترحة

| الأصل المنطقي | الحقول الأساسية |
|---|---|
| EtherSignalDefinition | SignalId، DisplayNameKey، AudioCueId، Radius، Priority، DiscoveryRule |
| InteractionDefinition | InteractionId، PromptKey، Conditions، Duration، Effects |
| NarrativeNodeDefinition | NodeId، EntryConditions، Choices، StateWrites، ExitEvents |
| PuzzleDefinition | PuzzleId، InputSet، ValidationRule، SuccessEffects، ResetPolicy |
| SaveSchema | SchemaVersion، WorldState، NarrativeState، PlayerState، Settings |

## 5. مبدأ الاتصال بين الأنظمة

تستخدم الأنظمة أحداثاً مسماة مثل `Ether.SignalDetected` و`Narrative.NodeCompleted` و`Puzzle.StateChanged`. لا يُسمح للنظام الصوتي بتعديل الحالة السردية مباشرة؛ يمر التغيير عبر حدث أو خدمة سردية معروفة. هذا يقلل الاقتران ويجعل تتبع الأخطاء ممكناً.

## 6. الأداء وقابلية التوسع

تُعالج الإشارات القريبة فقط ضمن نطاق نشط، وتُخفّض كثافة الفحص عند غياب الإدراك أو عند خروج اللاعب من منطقة الاهتمام. تُحفظ تعريفات البيانات في صيغ قابلة للمراجعة، وتُمنع المراجع الدائرية بين المناطق والأصول السردية. لا تُعتمد أرقام أداء نهائية قبل وجود نموذج أولي قابل للقياس.

## 7. قرار مؤجل

اختيار إطار الصوت، أسلوب إدارة الحوارات، وحدود استخدام Blueprints مقابل C++ تبقى قرارات مؤجلة حتى اعتماد متطلبات الفريق ومقياس المحتوى. يُسجل كل قرار نهائي في `planning/decision-log.md`.
